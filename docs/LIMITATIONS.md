# 已知限制

這是研究原型，以下限制都是刻意寫明的。把本平台說成「已可上線」之前，每一項都需要處理。

## 模擬與替身

1. **託管機構、基金行政、KYC 機構、穩定幣發行人都是帳本上的模擬角色。** 測試裡沒有任何真實資產、真實資金或真實身分審查。
2. **儲備數字靠託管機構申報。** 帳本保證「發行不超過申報的儲備」，不保證申報本身正確。正式環境需要獨立稽核師的定期確信報告，最好也上帳本。
3. **NAV 靠基金行政申報。** 帳本只檢查 NAV 是否新鮮，不檢查計算是否正確。
4. **法律結構在鏈下，本原型沒有。** 包括基金實體、公開說明書、投資人契約、過戶代理的登記資格。`offeringDocHash` 只是對文件的雜湊承諾。

## 模型本身

5. **過戶代理可以建立自己持有的份數而不經過帳冊。** 持有部位由「過戶代理＋持有人」簽署，持有人就是過戶代理自己時，它一個人就能建立。
   這要靠監理端持續對帳才能抓到（`Test.Setup:checkReconciles`）。可能的補強：
   - 讓過戶代理自有部位也要託管機構簽署；
   - 讓帳冊記錄每一筆發行，對帳改成逐筆比對。
6. **帳冊是熱點合約。** 每筆申購、贖回都要封存並重建 `FundRegister`，所以同一檔基金的申購贖回必須一筆一筆處理。過戶代理在正式環境應批次處理（例如每日截止後一次結算），而不是逐筆即時處理。次級市場交易不碰帳冊，不受影響。
7. **只有單筆上限，沒有每日總量上限。** 總量上限需要一個每筆交易都要更新的計數合約，會和交易互搶，所以沒有做。可以改成由場所在鏈下監控，或按時段分片計數。
8. **價格帶只在交易場所檢查。** 場外轉讓（`TransferOffer`）沒有價格，所以也沒有價格帶。
9. **凍結的是單一持有部位，不是投資人。** 被凍結的投資人如果還有其他部位，要逐一凍結；更乾淨的做法是在憑證或帳戶層級凍結。
10. **扣押只能扣給過戶代理自己。** 要轉給第三人，第三人必須先同意（也是 signatory），所以要再走一次轉讓。
11. **沒有使用 Canton 的 explicit disclosure。** 投資人透過 `readAs Public` 讀取公開條款；如果之後改為不設 Public 角色，就要改用 explicit disclosure。
12. **儲備聲明只有總值，沒有持倉明細**，所以 Rule 2a-7 的投資組合限制無法在帳本上檢查（路線圖第 4 項）。
13. **基金條款由過戶代理單方修訂。** 包括更換認可的 KYC 機構、交易場所、結算資產。監理機關看得到每一版，但帳本不要求它同意。正式環境可以讓重大條款修訂需要監理或受託人會簽。
14. **NAV 沒有單日變動上限。** 基金行政可以發布任意 NAV；帳本只要求它是正數且新鮮。

## 工具與部署

15. **Daml SDK 版本是 3.4.0-rc2（發行候選版）。** 撰寫環境只能從 Docker Hub 取得 SDK，而 3.4 的穩定版只透過 `dpm` 發布。換成穩定版時，要重跑全部測試與突變測試。
16. **還沒有部署到任何 Canton 網路。** 測試在 Daml Script 的 IDE ledger 上跑，它檢查授權與可見性的方式和 Canton 相同，但沒有網路延遲、節點設定、同步器（synchronizer）等現實因素。
17. **沒有前端、後端或錢包整合。**
